# Where is `schedule_templates` queried?

## Query that fails (507 – response too large)

```sql
SELECT id, term_id, system_type, elective_course_ids, elective_combination_hash,
       base_schedules, schedule_count, access_count, last_accessed_at,
       "createdAt", "updatedAt", preferences_hash, excluded_days,
       excluded_core_course_ids, preferred_instructors, is_generating,
       parent_hash, parent_template_id, is_parent, campus_track
FROM schedule_templates
ORDER BY schedule_templates.id
LIMIT 50
```

This exact query (all columns including `base_schedules`, `ORDER BY id`, `LIMIT 50`) **does not appear in this backend**.

## Where `ScheduleTemplate` / `schedule_templates` is used in the backend

| File | Usage | Query shape |
|------|--------|-------------|
| **scheduleTemplateController.ts** | `getAllTemplates` | **Raw SQL** – only metadata columns, no `base_schedules`, no limit 50 |
| **scheduleTemplateController.ts** | `existingParent = templateRepo.findOne({ where: [...] })` | `findOne` → `LIMIT 1`, not 50 |
| **scheduleTemplateController.ts** | `templateRepo.findOne` (checkTemplateExists, etc.) | `findOne` → `LIMIT 1` |
| **scheduleTemplateController.ts** | `templateRepo.delete(...)` | DELETE, not SELECT |
| **scheduleTemplateController.ts** | `templateRepo.create()` / `save()` | INSERT/UPDATE |
| **timetableViewController.ts** | Template lookup | **Raw SQL** – `SELECT id, schedule_count, base_schedules, ... WHERE ... LIMIT 1` (limit 1) |
| **scheduleTemplateService.ts** | `templateRepo.findOne(...)` | `findOne` → `LIMIT 1` |
| **scheduleTemplateService.ts** | `templateRepo.delete(...)` | DELETE |
| **data-source.ts** | Entity registration | No query |

There is **no** `getRepository(ScheduleTemplate).find({ take: 50 })` or any `.find()` on `ScheduleTemplate` that would produce `ORDER BY id LIMIT 50`.

## Likely source of the failing query

1. **Neon dashboard** – Browsing the `schedule_templates` table often runs something like `SELECT * FROM schedule_templates ORDER BY id LIMIT 50`. That matches the failing query and will hit the 64MB limit if `base_schedules` is large.
2. **Another client** – Any tool (pgAdmin, DBeaver, custom script, other app) that does `SELECT *` or “load first 50 rows” on `schedule_templates` will also select `base_schedules` and can trigger the same error.

## What to do

1. **Backend list endpoint** – Already fixed: `GET /api/timetable/admin/templates` uses raw SQL and does **not** select `base_schedules`.
2. **Neon / other clients** – Do **not** run `SELECT * FROM schedule_templates`. Either:
   - Use the view: `SELECT * FROM schedule_templates_list LIMIT 50` (no `base_schedules`), or  
   - Select only the columns you need and omit `base_schedules`.
3. **Migration** – Run `add_schedule_templates_list_view.sql` so the view `schedule_templates_list` exists. Then any client (including Neon table browser) can safely list rows by querying the view instead of the table.

## Summary

- The failing query is **not** generated by this backend.
- It is almost certainly from the Neon SQL/table UI or another DB client that selects all columns with a default limit of 50.
- Use `schedule_templates_list` (or explicit columns without `base_schedules`) for list-style access.
